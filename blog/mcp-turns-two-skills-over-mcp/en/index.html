Executive Summary

An MCP server used to hand over tools and stop there. It has now started handing over how to use them as well. On November 24, 2026, the day the Model Context Protocol turned two, Anthropic opened Skills over MCP as a public beta in Claude and Claude Code. Put skills next to tools on a server, and the model reads the matching instructions at the moment that work comes up.

The anniversary numbers are large. Monthly downloads of the Python, TypeScript, C#, Rust and Ruby SDKs passed 700 million over the past 30 days, against 90 million in the same month a year earlier. A download count tells you how widely MCP has been installed. It says nothing about whether the instructions servers have started sending are worth reading.

Sections 1 through 5 report what the official blog and the extension specification say. Section 2 separates what belongs to the MCP specification from what is a Claude product announcement. Section 6 is our reading.

The Numbers Published at the Two-Year Mark

MCP is the convention that defines how a model reaches tools and data outside itself. Anthropic open-sourced it on November 25, 2024, and the first revision of the specification carries the date 2024-11-05. The anniversary post reports the spread of the protocol in three lines.

  • Monthly downloads of the Python, TypeScript, C#, Rust and Ruby SDKs passed 700 million over the 30 days ending November 23. They were close to zero at launch and crossed 90 million by the first birthday in November 2025.
  • Cumulative downloads passed 5 billion, and more than 4.5 billion of those came in the past year alone.
  • Unique contributors, counted once each, passed 2,500.

The event numbers came out alongside them. The MCP Dev Summit held in New York in April 2026 drew about 1,200 people, roughly four times the first summit in San Francisco in May 2025. Meetups ran through ten cities across four continents, and Seoul in August 2026 was one of them. The most recent ran for two days in Nairobi.

The two-year timeline records the order in which the specification grew. The two rows worth watching while reading this announcement are the last two.

When What happened
November 2024 Anthropic open-sources MCP (specification 2024-11-05)
June 2025 Elicitation and structured output enter the specification (2025-06-18)

▲ Drawn from the timeline in the anniversary post. The orange row is the extension this article covers.

The post closes its opening section with Angie Jones, VP of Developer Experience at the Agentic AI Foundation. "Whether an agent is querying a database to fix a bug, or helping a researcher access the data they need, MCP servers have become part of the fabric of the agentic internet." She ends on the builders: when they get a stake in shaping the technology they use, everyone wins.

Our reading starts here. A download count does not distinguish an install from a reinstall, and it climbs every time an automated build pulls the dependency. So 700 million tells you that MCP has become a default component in a great many projects. It does not tell you that any given installed server is worth connecting to. When this blog drew 400 servers at random from the public registry in September 2026 and tried to start them, 48.8% completed initialization. Adoption figures and operating figures have to be read together.

Three Things Opened the Same Day, and Whose Public Beta It Is

Separately from the anniversary post, four items came out of the Claude product side the same day. Three are available now and one is a preview. The same post reports more than 10,000 usable MCP connectors. Each item carries a named customer, which makes it easier to judge what the feature is for.

Feature Status What it does Named users
Skills over MCP Public beta A server posts instructions for using its tools next to the tools themselves Shopify, HubSpot, Atlassian, Carta (coming)
Tasks Generally available Runs a long job or an agent loop in the background and collects the result when it finishes ZoomInfo
Elicitation Generally available Pauses mid-job to show the user a form or a link, then continues once an answer comes back Supabase, Railway, GitHub
File Uploads Shipping soon Sends PDFs, spreadsheets and images straight to the server without passing through the context window —

▲ Statuses and named users as written in the Claude product post of November 24, 2026.

The four names in the first row show what kind of instructions a server ships. Shopify sends store design, HubSpot sends customer onboarding, and Atlassian sends the context of a team's own organization. Carta is described as preparing a skill that drafts equity paperwork. None of the four is a single tool call; each walks through several steps. In the second row, ZoomInfo uses Tasks to run deep account and contact research in the background.

The Elicitation examples show most clearly what that feature is meant to prevent. Supabase confirms cost before creating a paid project and before running irreversible SQL, Railway asks before changes such as removing a service, and GitHub makes the user type the repository name by hand before an agent deletes it.

2.1"Public Beta" and "GA" Are Product States

One distinction is worth making before going further, because the same words point at two different things on two different layers.

  • The specification layer — SEP-2640, the basis for the Skills extension, was merged as Final on September 13, 2026, and the extension itself sits at the Beta stage of the lifecycle. Beta means breaking changes are allowed. The anniversary timeline also records it as "Skills over MCP beta in October."
  • The product layer — The public beta of November 24 means the feature opened in the Claude and Claude Code products. The "generally available" labels on Tasks and Elicitation likewise describe product rollout status.

Tasks never appears in the anniversary post. Elicitation appears only as a timeline row saying it entered the specification in June 2025. Read the two posts as one event and the sentence "the MCP specification made Tasks generally available" assembles itself easily, but nowhere is that written.

One more note for readers who follow sources. The anniversary post landed in the specification repository as PR #3584. Its title is "docs(blog): celebrate two years of MCP" and the only files it changes are the blog post and its images. It is the PR that published the post, not a PR that changed the specification, so the basis for the Skills extension is SEP-2640 and the modelcontextprotocol/ext-skills repository.

3

The Server Sends the Instructions

Until now an MCP server handed the model two kinds of thing: a list of actions it could take (tools) and material it could pull in (resources). A third slot has appeared, holding instructions for the order in which this server's work gets done (skills). Whether the job is processing a refund or reviewing code, anything that mixes several tool calls with conditional branches needs more than "here is what you can do." It needs "when this happens, do it this way."

The three slots carry different loads. The diagram below shows that division and when the instructions get read.

Technically the extension digs no new channel. It sits on top of resources, which already existed. Each file in a skill directory is exposed as a resource, addressed by convention with a skill:// URI, and read through the ordinary resources/read. Only three methods are new: skills/list to browse what a server holds, skills/get to fetch one by name, and the optional resources/directory/read to list the immediate children of a directory.

The shape of a skill is not this extension's business. The specification says directly that directory layout, frontmatter format, naming rules and progressive disclosure are left entirely to the Agent Skills specification, and that this extension defines only how to carry those over MCP. That is why a skill file written for local use can go straight onto a server.

The product-side explanation frames the benefit as context usage. A server can carry many skills, and the ones not in use at that moment never enter the context window. "Read only when needed" is not an implementer's choice but a requirement of the specification. A host must not fetch skill files ahead of time, not on connecting, not on listing, not on approval. SKILL.md arrives when the skill loads, and attached files arrive when they are actually read. All that appears in a listing is the name, the description, and a size and digest for each file.

On the Claude product side, availability splits by plan. It is on by default for Pro, Max and Ultra, a Team admin has to turn it on, and Enterprise is listed only as "coming."

4

Skills You Install and Skills That Arrive

A skill itself is not a new object. Handing an agent a directory of written instructions was already common practice. What changed is where that directory comes from. Instead of a person downloading it onto their own machine, a server offers it to whichever client connects.

The shortest statement of that difference from practice comes from Filipe Motta, a senior DevOps engineer. "The server that exposes your Terraform or Kubernetes tools can also carry the runbook for using them well," he wrote. "When it changes there is nothing separate to update on each laptop."

Item Skill you download and install Skill the server sends
Install The user does it on every machine None. Connect to the server and it appears in the list
Update The user fetches it separately The server edits it and the next read picks it up
Unit of approval The act of installing One skill, and the exact set of files it had at that moment
When the content changes Nothing changes until the user fetches it The earlier approval is revoked and the user is asked again
Declared permissions Applied as written in the file Ignored unless the user grants them separately

▲ The right column is drawn from the security requirements of the Skills extension specification. The left column describes how local skills are usually run.

The bottom two rows are where the extension put most of its care. Once a user approves a skill, that approval is bound to the set of files at that moment, and precisely to every file's URI and content digest. If the next listing describes a different set, whether one file changed or files were added or removed, the host must treat the earlier approval as revoked and ask again. The specification writes this as a MUST, not a recommendation.

The permissions rule is blunter. The local skill format has a field declaring which tools a skill may use, and the specification says a host must ignore that field on a skill that arrived over MCP. The reason given is that a remote server filling in that field is not describing its own environment but demanding privileges on someone else's machine. It applies only where the user has explicitly granted it for that skill.

A digest is not a signature, though. As the specification states outright, the digest and the content come from the same server. Their agreement means only that the two are consistent with each other, not that the content can be trusted, and a gateway standing in the middle could rewrite both at once. The specification is explicit that digest matching must not be treated as a security boundary.

How actual hosts took this is public too. Claude Code ignores the parts of a server-sent skill's declared configuration that concern tool permissions and hooks, and in the default auto mode a classifier decides whether to load the skill without asking. A user can block skills from a particular server or set a rule to confirm every time, and an administrator setting can turn the whole thing off across an organization.

5

How Open Is It

Meeting this news through the Claude product blog, it reads easily as Anthropic bolting one feature onto its own product. Open the specification side and it does not. The extension is named io.modelcontextprotocol/skills, its basis is SEP-2640, and the Skills Over MCP Working Group maintains it in a public repository. Meeting notes, decision records and design rationale documents sit in the same place.

The license splits in two. Code is under Apache License 2.0, and documentation other than code is under CC BY 4.0. The repository's license file carries both. Anyone may read this specification, implement it, translate it, and put it into their own product.

Open does not mean settled. The extension stage is Beta, and the repository states that Beta revisions may introduce breaking changes. The base protocol revision is 2026-07-28. An implementation wired up now may need rework at the next revision.

5.1Who Has Already Implemented It

The implementation list the working group maintains carries 108 rows across four groups, covering SDKs, servers, gateways and hosts, and 64 of those rows are marked as already implementing the published Beta specification. The rest are in progress, partial, or at the request stage. It is a community-maintained list and some entries are self-reported, so it is more useful for seeing which camps have shown up than for the count itself.

  • Official SDKs — TypeScript, C#, Rust and Ruby are already in released versions, and Python is merged but not yet released. Java, Kotlin, Go and PHP are in progress.
  • Servers — 45 rows, among them the GitHub MCP server, Cloudflare, Hugging Face, Google's MCP Toolbox, n8n and Glean.
  • Hosts — VS Code has it on by default since 1.147, with per-server consent. That is the same VS Code that GitHub Copilot runs in. Claude Code has been in public beta since v2.1.331, invoking server skills as /<server>:<skill> with approval taken per version.
  • Not yet — ChatGPT and Codex are listed as planned. Skill import at plugin submission was rolled back in November 2026 and deferred until support ships across both products.

Our reading: the specification belongs to no single company and has been taken up widely enough that Microsoft turns it on by default, yet most people using this feature today reach it through either Claude or VS Code. An open specification and an even ecosystem are not yet the same statement.

6

Why Pebblous Is Watching This Change

One line sits in the security section of the specification: skills are data, not instructions. It is the heading on a requirement that a host must not treat skill resources with higher authority than any other context. The item just above it is blunter. Skill content is instruction text delivered to a model, which makes it a prompt injection surface, and a host must treat it as untrusted input and regard it as riskier than a remote tool call.

Take the authors at their word that this is data, and a question follows. If it is data, who looks after its quality?

The specification's machine validation does not answer that. By the repository's own account, the published JSON schema checks structure only. Digest integrity, completeness of the file list, agreement between a URI and the name in the frontmatter, and the consent requirements are prose-only requirements that the schema cannot enforce, and the repository says semantic conformance tests and host-side checks are needed separately. What the machine sees is shape. Whether the content says the right thing, nobody checks.

What this changes inside a company was put in one sentence by Guillaume Lebedel, co-founder and CTO of StackOne. "Approving an MCP server mostly meant approving what it can do," he wrote. "Now it also means approving what it tells the agent to do." In the same article a developer, Jeff Allen, points at the cost: "auto-loading the wrong stuff into context gets expensive fast."

Seen from data quality work, this shape is familiar. It is how it always goes with problems that look fine one record at a time and go wrong in aggregate. Any single skill may be a well-written document. But let one organization open five servers that each carry five skills, and the same customer identifier ends up called a customer number in one place and an account ID in another. A human reader would step over the gap; an agent believes both and uses both. Missing values and outliers show up in a single row, while duplicates and inconsistencies only show up once you gather the rows. That applies here unchanged.

Where the responsibility lands is clear enough too. The specification loaded the host with MUSTs: do not prefetch, bind approval to content, ignore declared permissions, show provenance. There is no MUST about whether the instructions are correct, and there could not be. That part stays with the organization running the server. If you have decided to open an internal system over MCP, the accuracy of the documents you send with it is no longer a security setting but your own responsibility.

6.1Three Things to Check Before Opening an Internal System Over MCP

All three fall out of requirements confirmed above. The specification's machine validation does not look at the content of the instructions, one changed file revokes an approval, and where terms diverge an agent carries the divergence along. These are checkable right now.

  • Does that "how to use it" exist as a document today? If it lives only in one person's head and a Slack thread, there is nothing to put on the server. Open the tools first and write the instructions later, and in between the agent moves on guesses drawn from the schema alone.
  • Who edits that document, and who reviews it? A single changed file revokes client-side approval and raises a fresh prompt for the user. Fixing one typo becomes a deployment that asks every user to approve again. That is why a document change needs a release process attached to it.
  • Do the tool names, the field names and the instructions use the same words? If you plan to open several servers, settle this first. Open them with the terms already diverging and the agent learns the divergence and uses it.

The scope is worth stating plainly. Every figure in this article comes from the parties that announced it, and we did not measure any of it again. The implementation list is community-maintained and partly self-reported. The extension is at Beta, so some of the requirements written down here may differ in the next revision.
