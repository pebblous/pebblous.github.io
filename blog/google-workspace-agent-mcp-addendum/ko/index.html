Executive Summary

구글이 AI 에이전트가 구글 워크스페이스 데이터에 닿는 길을 전용 통로 두 개로 좁혔다. 구글은 11월 25일 공식 블로그에서 Workspace MCP 서버와 Workspace CLI를 정식 공개했고, 같은 날 약관 부속서 'Workspace AI Tools Addendum'을 내놨다. AI 에이전트는 기존 REST API 대신 이 두 통로로 지메일·드라이브·문서도구에 접근해야 한다. 사람이 쓰는 일반 앱은 기존 API를 계속 쓴다.

부속서는 에이전트가 가져간 데이터의 쓰임도 묶었다. 워크스페이스 데이터로 모델을 학습시키거나 미세조정할 수 없고, 임베딩 같은 파생 데이터는 30일을 넘겨 보관할 수 없다. 연결을 끊으면 데이터를 지워야 한다. 기술적 강제는 2027년 2월 1일, 사용량 과금은 4월 1일에 시작한다.

구글이 내건 이유는 유효한 OAuth 토큰을 곧 사용자의 의도로 보던 전제가 에이전트 앞에서 무너졌다는 것이다. 기업 데이터에 붙는 에이전트마다 누구 권한으로 들어왔고 무슨 기록을 남기는지가 이제 약관 문제가 됐다.

주요 수치

아래 네 숫자가 이번 조치의 뼈대다. 전용 서버가 열린 앱은 여덟 개이고, 에이전트가 만든 파생 데이터는 30일 안에 지워야 한다. 날짜는 둘이다. 2027년 2월 1일부터 규칙이 기술적으로 걸리고, 4월 1일부터 돈이 붙는다.

1

구글 워크스페이스 MCP 서버·CLI 정식 공개

구글은 11월 25일 워크스페이스 블로그에 "신뢰와 통제를 위해 만들었다"는 제목의 발표문을 올렸다. 발표의 중심은 두 도구다. Workspace MCP 서버는 개방형 규격 MCP(Model Context Protocol)를 따르는 구글 관리형 서버로, 클라우드와 웹에서 도는 에이전트가 지메일·드라이브·문서·시트·슬라이드·캘린더·채팅·할 일 여덟 개 앱에서 작업하게 한다. 구글 킵은 나중에 붙는다.

구글에 따르면 MCP 서버는 파일이나 메일을 통째로 내려보내지 않고, 워크스페이스 보안 경계 안에서 작업에 필요한 맥락만 돌려준다. Workspace CLI는 사용자 컴퓨터에서 도는 로컬 에이전트와 터미널 자동화용이다. 범위를 좁힌 로그인으로 들어가고, 결과를 구조화된 JSON으로 내놓는다.

같은 날 구글은 약관도 바꿨다. 구글 API 서비스 약관에 붙은 부속서 Workspace AI Tools Addendum 첫 조항은 워크스페이스에 접근하는 도구가 "AI 에이전트이거나 AI 에이전트가 구동하는 경우 구글 MCP를 써야 한다"고 정했다. 구글 클라우드 블로그는 같은 내용을 "AI 에이전트는 기존 REST API가 아니라 Workspace MCP 서버나 Workspace CLI를 써야 한다"고 적었다.

2

구글이 밝힌 이유, OAuth 토큰과 사용자 의도

구글 클라우드는 보안 블로그 글 「기업에 에이전트를 안전하게 배치하기」에서 이유를 설명했다. 기존 REST API는 사람 속도로 움직이는 앱을 위해 만들어졌고, 그 세계에서는 유효한 OAuth 토큰이 곧 사용자의 의도를 뜻했다. 구글은 "AI 에이전트가 정보를 읽는 데서 그치지 않고 메일·문서·데이터셋·클라우드 인프라를 오가며 기계 속도로 스스로 행동하게 되면서, 유효한 토큰만으로는 더 이상 충분하지 않다"고 썼다.

워크스페이스 발표문은 위험을 구체적으로 들었다. 에이전트가 토큰으로 사용자가 의도하지 않은 작업을 하거나, 관리자 눈에 띄지 않게 데이터를 밖으로 옮기거나, 관리자가 손쓰기 전에 기계 속도로 데이터를 빼내고 고칠 수 있다는 것이다. 토큰이 탈취되면 에이전트가 내부자 위협이 된다고도 했다. 구글 클라우드는 "에이전트가 쉬지 않고 도는 상황에서 한 번 띄우는 동의 화면으로는 부족하다"고 적었다.

새 통로에서는 검사가 요청 경로 안에 들어간다. 구글에 따르면 MCP 서버는 호출마다 조직 권한과 데이터 유출 방지(DLP) 규칙, 분류 라벨을 확인하고, 메일 발송이나 공유 권한 변경 같은 민감한 작업은 사람의 확인을 거친다. 에이전트가 아닌 일반 OAuth 클라이언트의 호출은 거절한다. 개발자는 OAuth 클라이언트를 만들 때 "AI 에이전트용"이라고 표시해야 한다.

3

AI Tools Addendum의 금지 조항

부속서는 11월 24일 마지막으로 개정됐다. 1조가 에이전트가 들어오는 길을 정했다면, 2조는 들어와서 가져간 데이터로 무엇을 할 수 없는지를 정한다. 학습, 장기 보관, 연결을 끊은 뒤의 보관, 긁어 가기, 승인받지 않은 용도가 차례로 막혔다. 2조가 에이전트 개발사에 금지하는 일은 다음과 같다.

  • 워크스페이스에서 가져온 사용자 데이터나 구글 기술 정보를 모델 학습·미세조정에 쓰는 일
  • 구글 기술 정보를 30일 넘게 저장하는 일. 구글 기술 정보에는 워크스페이스 접근으로 얻은 벡터 임베딩, 메모리 색인, 사용자 프로필, 조직 관계도가 들어간다
  • 사용자가 도구 연결을 끊거나 권한을 거둔 뒤에도 사용자 데이터와 구글 기술 정보를 남겨 두는 일
  • 워크스페이스 접근 지점과 구글 MCP, 그 문서와 출력물을 긁어 가거나 체계적으로 탐색하는 일
  • 사용자가 승인한 진행 중 작업 외의 목적으로 데이터를 처리하는 일

이 가운데 실무에 가장 크게 닿는 조항은 30일 한도다. 메일과 문서를 임베딩해 벡터 데이터베이스에 쌓아 두고 검색하는 방식의 에이전트라면, 그 색인도 구글 기술 정보에 들어가므로 30일을 넘겨 들고 있을 수 없다. 워크스페이스 데이터를 자사 저장소로 옮겨 오래 쌓아 두는 설계는 이 약관 아래에서 성립하기 어렵다.

분류를 피하는 길도 막았다. 부속서는 에이전트를 배치하고 도구를 호출하는 소프트웨어 계층을 'AI 하네스'로 정의하고, 하네스나 AI 모델이 구동하는 도구도 MCP 의무 대상에 넣었다. 도구를 위장해 이 분류나 MCP 의무를 빠져나가는 일은 금지다.

4

2027년 2월 강제, 4월 과금

구글 발표문에 따르면 기술적 강제는 2027년 2월 1일 시작한다. 새 통로에는 Standard와 Scaled 두 사용 티어가 생겼다. 개발자 해설 기사들이 전한 구글 개발자 문서 내용을 보면, 이날부터 REST API를 직접 부르는 에이전트는 어떤 사용 티어를 골랐든 Standard 티어 쿼터로 묶인다. 사용량 과금은 2027년 4월 1일 Scaled 티어부터 붙는다.

REST API가 없어지지는 않는다. 구글은 사람과 일반 앱을 위해 설계한 기존 방식과 AI 에이전트를 따로 표시해 관리하겠다고 밝혔다. AI가 끼지 않은 야간 백업 작업이나 정해진 대로만 도는 스크립트는 기존 API를 그대로 쓴다. 기존 서비스에 에이전트 기능을 더한 개발사는 에이전트용과 일반용 OAuth 클라이언트를 나눠야 한다.

관리자 쪽 기능도 함께 나왔다. 워크스페이스 관리자는 관리 콘솔에서 에이전트를 보고, 감사하고, 권한을 거둘 수 있다. 사용자가 자기 메일과 파일에 붙은 에이전트 활동을 보고 끊는 기능, 특정 지메일 메시지나 드라이브 폴더를 외부 에이전트에게서 가리는 기능은 "곧" 나온다고만 했고 날짜는 밝히지 않았다.

5

구글 클라우드 Agent Identity, 에이전트에 따로 주는 신원

워크스페이스 조치는 구글 클라우드의 에이전트 보안 묶음과 같은 날 나왔다. 구글 클라우드 블로그에 따르면 에이전트는 Agent Registry에 등록된 자기 신원 Agent Identity를 받는다. 여러 에이전트가 함께 쓰는 키나 오래 사는 키는 없고, IAM 정책과 조직·프로젝트 단위 쿼터가 권한을 묶는다. 이 신원은 메일이나 파일에 닿을 때 사용자가 위임한 권한을 실어 워크스페이스로 들어간다.

Agent Gateway는 LLM·MCP·A2A(에이전트 간 통신) 트래픽 전용 관문으로, 요청마다 에이전트 신원을 등록부와 대조하고 기본 차단 규칙을 적용한다. 구글은 클라우드 Agent Identity나 OAuth 권한을 거두면 접근이 즉시 멈춘다고 밝혔다. 이상 행동은 Security Command Center와 Cloud Audit Logs가 잡는다.

사내 데이터에 에이전트를 붙인 팀이 지금 확인할 것은 두 가지다. 에이전트가 직원 계정의 토큰을 빌려 들어오는지, 따로 받은 신원으로 들어오는지. 그리고 감사 기록에 에이전트와 권한을 위임한 사람이 함께 남는지. 워크스페이스는 2027년 2월부터 이 두 질문에 약관으로 답을 요구한다.
