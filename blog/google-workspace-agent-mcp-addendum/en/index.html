Executive Summary

Google has separated the AI agents that reach Workspace data from the apps people drive by hand. The Workspace MCP servers and the command line tool (CLI), released in general availability on November 25, 2026, are the only door left open to agents, and the Workspace AI Tools Addendum published alongside them sets out how far the data taken through that door may be used. Apps a person clicks through keep calling the REST APIs as before. It is the agents whose position changes.

The deadlines for the change came with it. Technical enforcement begins on February 1, 2027, and billing on the usage tiers begins on April 1. What the addendum asks falls more on use than on route. Workspace data and anything derived from it may not be used to train or fine-tune a model, the derived information may not be held past 30 days, and scraping the APIs is out. When a customer disconnects an agent, the data taken has to go.

Sections 1 through 4 are facts confirmed in the Google Workspace announcement, the Google Cloud blog, the Workspace Updates post, and the full text of the addendum. The clause distinctions and the wording in section 4 were compared directly against the addendum itself. Section 5, which reads this change as a move from borrowing a person's account to giving an agent an identity of its own, is this article's interpretation.

1

Agents Now Have a Door of Their Own

Google shipped the Workspace MCP servers and the Workspace CLI in general availability on November 25. The MCP servers connect eight apps: Gmail, Drive, Docs, Sheets, Slides, Calendar, Chat and Tasks. Keep follows soon. The CLI is the side meant for agents running on a laptop or a server and for automation driven from a terminal. It returns structured JSON and narrows the scopes it asks for at sign-in.

The terms published in the same post are the Workspace AI Tools Addendum. They require an AI agent reaching Workspace data to go through an MCP server or the CLI instead of calling the REST APIs directly. The requirement lands on agents, not on all software. An app running in front of a person keeps the APIs it uses today.

A marker that tells the two apart arrived as well. OAuth 2.0 client settings in the Google Cloud console now carry a checkbox reading "Use this client for an AI-powered agent," which is stored in the configuration as is_agentic. The guidance alongside it says traditional non-agent features should use a separate client. The MCP servers refuse clients that are not marked as agents, and they interlock with Model Armor, Google Cloud's prompt injection screening service. A company running both an agent and an ordinary app will have to take apart any setup that drives the two on a single credential.

2

When One Valid Token Meant the User Wanted It

Why a separate route is being cut at all is set out in one paragraph on the Google Cloud blog, written jointly by Chandu Thota, VP, Engineering, Workspace, and Brad Calder, President, Google Cloud Platform and SRE.

Traditional REST APIs were built for human-paced apps where a valid OAuth token implied user intent. As AI agents shift from reading information to acting autonomously at machine speed across email, documents, datasets, and cloud infrastructure, a valid token is no longer enough. Policy checks, data boundaries, and human confirmation have to live in the request path.

Source: Google Cloud, "Deploying agents safely in your enterprise" (November 25, 2026).

The paragraph holds an assumption and the point where it gives way. The assumption is that the person who handed over the token wants this particular thing done right now. Back when every click sent one request, that held almost always. An agent fires requests long after a person approved once, at a speed no person can read along with. The token is still valid, but it says nothing about whether a person wanted that particular request.

The same post puts a number on how much rides on that assumption. Workspace APIs now handle more than 2.8 trillion calls a month. Public Drive API traffic alone is more than two and a half times the volume of 2022, and more than 18 billion reads from Drive each day come from API callers rather than from a person's screen. The rule that reads one token as a person's intent applies to every one of those calls.

So the answer Google picked is to move the checking into the request path. The upper half of the diagram below is the route as it stands, and the lower half is the route agents have to take from February 2027.

3

An Agent Has to Ask Before a Big Action

The announcement groups what is arriving into six protections, and the Google Cloud blog walks through the same six beside the matching pieces on the cloud side. The first four are available now, the fifth is still pending, and the sixth is the addendum.

  • • A policy check on every request. Each call passing through an MCP server or the CLI is checked against the organization's permissions, its data loss prevention (DLP) rules, and the classification labels attached to documents.
  • • Identities and limits given to agents separately. External agents get dedicated OAuth client IDs, least-privilege scopes and usage quotas. Time-limited approvals are listed as not yet available.
  • • A person confirms high-impact actions. Sending external email, changing Drive sharing permissions and making bulk edits are the examples given. Confirmations that external agents collect follow the IT policies set in Workspace, and admins define those confirmation rules in the admin console.
  • • Visible, and revocable. Admins view, audit and revoke agents from the admin console. The ability for a user to see agent activity on their own mail and documents and cut it off is still to come.
  • • Boundaries around sensitive content (coming soon). External AI agents can be blocked from reaching specific Gmail messages and specific Drive files and folders. It is a layer on top of the existing data loss prevention and client-side encryption.
  • • Limits on data use beyond Workspace. What may not be done with the data once taken is written in the addendum. That is the next section.

Put in a single sentence, the six amount to pulling the agent out of the category of people and apps and standing it up as a subject of its own. An identity has to exist before a limit can be attached, a limit has to exist before records split apart, and records have to split before a single one can be cut off. On the Google Cloud side the same design is built as Agent Registry, which issues each agent a distinct identity, and Agent Gateway, which verifies that identity and blocks outbound calls by default.

4

Seven Prohibitions in the Addendum, the Dates Elsewhere

The announcement summarizes the prohibitions in three items: permanently storing raw Workspace data, training models on that data, and scraping the Workspace APIs. Two obligations come with them. Derived data has to be removed within a strictly defined window, and data has to be deleted when a customer disconnects.

The addendum itself breaks the same ground into seven prohibitions. The first four bear on how the data is held. User data may not be stored in a way the Workspace API policies prohibit, and it may not be processed for any purpose other than delivering the action the user has currently authorized. Google Technical Information, which is the derived material, may not be stored for more than 30 days, and its processing is bound to the same scope. After a tool is disconnected or its access is revoked, neither the user data obtained nor the derived information may be retained.

The last three look at what is done with that data. Scraping or systematically probing the access points, the Google MCPs, or any of their skills, documentation and outputs beyond what the authorized action needs is blocked. The training ban is not model training alone: fine-tuning, building evaluation datasets and model distillation sit on the same line. Using the data to develop a product or service similar to a Workspace service is on the same list. If Google reasonably believes any of these has happened, it may restrict or remove that tool's access immediately, and where it judges this necessary to stop the activity, it may suspend or terminate the customer's access itself. Google can act before a violation is established.

One thing here has to be kept separate. The 30 days attach to Google Technical Information, not to user data. The addendum defines that term to cover vector embeddings, memory indexes, user profiles, organizational graphs and even the failure patterns accumulated from calling the access points, and then states plainly that it does not include any user data. What binds user data is not a date but purpose and connection state. It cannot be used outside the authorized action, and it cannot be retained once the connection ends.

How the addendum decides who is covered is worth a look too. The requirement to use a Google MCP does not land on agents alone. A tool is covered if it is an AI agent, or if it is driven by an AI harness, the software layer that launches agents, calls tools and stitches the work of several agents together, or by an AI model or a model-backed service. In the very next sentence the addendum says not to blur the character of a tool in order to dodge that classification. It is the sentence a self-declared category inevitably needs, since developers mark their own clients as agents or not.

4.1The Day Enforcement Starts and the Day It Costs Money

The two dates differ in kind. February 1, 2027 is when the obligation to use the MCP servers or CLI starts being technically enforced. On April 1, 2027, scaled tier billing begins for the Gmail, Calendar and Drive APIs, the Workspace CLI and the MCP servers. Charges apply only to the portion above the daily free usage.

There are two tiers. The standard tier is free within published usage limits, and a project that needs more than that has to be marked as internal by an admin or moved to the scaled tier by a billing administrator. A project that takes no action by April 1, 2027 has its limits changed automatically to the standard tier limits, at no additional cost. Google writes that over 99% of active developers already sit inside the standard tier and will see no change in cost. The tiers start with Gmail, Drive and Calendar, and the remaining access mechanisms follow over the coming months.

What exactly happens to an agent that keeps calling the REST APIs directly after February 1, 2027 is not written in any of the sources. No sentence separates blocking from throttling from treatment as a breach of terms, and the reporting varies on it. The dates themselves are not all in one place. February 1 does not appear in the addendum. The addendum carries the obligation to use the route and the list of prohibitions, while the technical enforcement date sits in the announcement and the Workspace Updates post. What is certain today is that the obligation now exists, and the two dates.

5

Why Pebblous Is Watching This

Even for the same data, the identity it came in under changes what may later be done with it. When the way in is a user account token, the name left in the audit log is a person's. Once the documents that person opened and the documents an agent read pile up in the same column under one name, telling later which of them was whose act is hard. A dedicated client ID splits that column, so the log keeps the fact that the caller was an agent and which agent it was. That is what makes cutting off one of them possible.

The same problem has come up elsewhere in the same shape. The security firm Arrakis pointed out that an unused agent's credentials keep reaching company material as long as they stay alive, and Federal Reserve Governor Michael Barr warned that banks cannot tell whether the party entering an account is a person or an agent. On the public side, Korea's Personal Information Protection Commission counted 3,164 cases of logging in on a user's behalf to pull records and announced a shift to APIs from 2027. Closing the route where automated tools entered on a person's credentials, and attaching a separate name to whoever enters, is happening in the private and public sectors at the same time.

For organizations that handle data, the training ban is the clause that creates work right away. If documents pulled from Workspace were turned into search embeddings and parked in a vector database, those embeddings are the derived data the addendum speaks of. The addendum says not to hold it past 30 days, so an index built once and reused for months has to be looked at starting from its retention cycle. A design that deletes only the source documents when a customer disconnects, leaving the embeddings and the memory index behind, is at odds with the terms. In a pipeline that never recorded data provenance per connection, answering which vector came from which customer is the first hard question.

So what to check now is which identity our own agents use to reach other people's data, what we built from what we took and where it is kept, and whether a procedure exists to delete both when a connection ends. Changing routes has until February 2027, but retracing what was built out of data already taken cannot be started then if no record was kept. Other writing on agents is gathered in the AI agent series, and the specification side is in the piece on MCP turning two.
