Executive Summary

Google has narrowed the ways an AI agent can reach Google Workspace data to two dedicated channels. In a November 25 Workspace blog post, the company made the Workspace MCP server and the Workspace CLI generally available, and on the same day it published a new terms annex, the Workspace AI Tools Addendum. AI agents must use these two channels, not the existing REST APIs, to work with Gmail, Drive and Docs. Ordinary apps used by people keep the existing APIs.

The addendum also limits what agents can do with the data they collect. Workspace data can't be used to train or fine-tune models, derived data such as embeddings can't be kept longer than 30 days, and everything must be deleted when a user disconnects the tool. Technical enforcement starts on February 1, 2027, and usage-based billing on April 1.

Google's stated reason is that the old assumption, a valid OAuth token equals the user's intent, no longer holds once agents act on their own at machine speed. For any agent connected to company data, whose authority it uses and what record it leaves have now become questions of contract terms.

Key Figures

Four numbers frame the change. The dedicated server covers eight apps, and derived data an agent builds must be gone within 30 days. Then there are two dates: rules are enforced technically from February 1, 2027, and charges begin on April 1.

1

Google Workspace MCP Server and CLI Go GA

On November 25, Google posted an announcement on the Workspace blog under the headline "Built for trust and control." It centers on two tools. The Workspace MCP server is a Google-managed server built on MCP (Model Context Protocol), an open standard, and it lets agents running in the cloud or on the web work across eight apps: Gmail, Drive, Docs, Sheets, Slides, Calendar, Chat and Tasks. Google Keep will be added later.

Google says the MCP server doesn't hand over whole files or mailboxes. It returns only the context a task needs and keeps the work inside Workspace's security boundary. The Workspace CLI is for local agents running on a user's own machine and for terminal automation. It signs in with narrowly scoped access and returns results as structured JSON.

Google changed its terms on the same day. The first clause of the Workspace AI Tools Addendum, an annex to the Google APIs Terms of Service, says that a tool accessing Workspace must use Google MCP "if it is an AI agent or is powered by an AI agent." The Google Cloud blog put it more bluntly: AI agents must use the Workspace MCP server or the Workspace CLI, not the existing REST APIs.

2

Google's Reason: OAuth Tokens and User Intent

Google Cloud laid out its reasoning in a security post titled "Deploying agents safely in your enterprise." The existing REST APIs were built for apps that move at human speed, and in that world a valid OAuth token stood in for the user's intent. Google wrote that as AI agents go beyond reading information and start acting on their own at machine speed across email, documents, datasets and cloud infrastructure, a valid token alone is no longer enough.

The Workspace announcement named the risks. An agent holding a token could take actions the user never intended, move data out without administrators noticing, or pull and modify data at machine speed before anyone can step in. A stolen token, Google added, turns an agent into an insider threat. Google Cloud also noted that a one-time consent screen falls short when agents run around the clock.

On the new channels, the checks sit inside the request path. According to Google, the MCP server checks organizational permissions, data loss prevention (DLP) rules and classification labels on every call, and sensitive actions such as sending email or changing sharing settings require a person to confirm. Calls from ordinary OAuth clients that aren't agents are rejected. Developers have to mark an OAuth client as "for AI agents" when they create it.

3

What the AI Tools Addendum Bans

The addendum was last revised on November 24. Where clause 1 sets the route an agent must take in, clause 2 sets what it can't do with the data once it has it. Training, long-term storage, keeping data after a disconnect, scraping and unapproved uses are all ruled out. Under clause 2, agent developers may not:

  • use user data obtained from Workspace, or Google technical information, to train or fine-tune models
  • store Google technical information for more than 30 days. That category covers vector embeddings, memory indexes, user profiles and organizational relationship maps derived from Workspace access
  • retain user data or Google technical information after a user disconnects the tool or revokes its access
  • scrape or systematically crawl Workspace endpoints, Google MCP, or their documentation and outputs
  • process data for any purpose other than the active task the user approved

Of these, the 30-day cap will hit day-to-day engineering hardest. An agent that embeds mail and documents into a vector database for retrieval would be holding Google technical information in that index, so it can't keep it past 30 days. Designs that copy Workspace data into a company's own store and keep it there are hard to square with these terms.

The addendum also closes off ways around the classification. It defines the software layer that deploys an agent and calls tools as an "AI harness," and it puts tools driven by a harness or an AI model under the MCP requirement. Disguising a tool to dodge the classification or the MCP requirement is prohibited.

4

Enforcement in February 2027, Billing in April

Google's announcement puts the start of technical enforcement at February 1, 2027. The new channels come with two usage tiers, Standard and Scaled. Developer write-ups citing Google's developer documentation say that from that date, agents calling the REST APIs directly will be held to the Standard tier quota no matter which tier they chose. Usage-based billing starts on April 1, 2027, beginning with the Scaled tier.

The REST APIs aren't going away. Google said it will flag and manage AI agents separately from the existing approach, which was designed for people and regular apps. A nightly backup job with no AI involved, or a script that only does what it was told, keeps using the existing APIs. Developers who have added agent features to an existing product will need separate OAuth clients for the agent side and the regular side.

Admin tools shipped alongside. Workspace administrators can see, audit and revoke agents from the Admin console. Two more features are only promised "soon," with no date: a way for users to see and cut off agent activity on their own mail and files, and a way to hide specific Gmail messages or Drive folders from outside agents.

5

Google Cloud Agent Identity Gives Agents Their Own Credentials

The Workspace changes landed the same day as a package of agent security features from Google Cloud. According to the Google Cloud blog, each agent gets its own identity, Agent Identity, registered in the Agent Registry. There are no keys shared across agents and no long-lived keys; IAM policies and organization- and project-level quotas bound what an agent can do. When the agent touches mail or files, it enters Workspace carrying the authority a user has delegated to it.

Agent Gateway is a dedicated entry point for LLM, MCP and A2A (agent-to-agent) traffic. It checks each request's agent identity against the registry and applies deny-by-default rules. Google says revoking a Cloud Agent Identity or its OAuth grant stops access immediately. Security Command Center and Cloud Audit Logs pick up abnormal behavior.

Teams that have connected agents to internal data have two things to check now. Does the agent get in by borrowing an employee's token, or with an identity of its own? And does the audit log record both the agent and the person who delegated authority to it? From February 2027, Workspace will require an answer to both questions as a condition of its terms.
