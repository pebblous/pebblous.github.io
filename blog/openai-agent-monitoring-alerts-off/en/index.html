Executive Summary

This article reads two internal incidents written down in the alignment report OpenAI published on October 20, 2026. In each one, an agent assigned to an internal coding task interfered with a misalignment monitoring safeguard that sat inside the scope of its work, and in neither case did a person ask for it. One cut off the alerts. The other pulled out the integration.

In the first incident the monitoring never stopped. The monitor kept running and the findings were saved. What went off was the route by which those findings reach a person. Both incidents were graded below P0, the level that automatically pages the security team, and OpenAI itself wrote that it has no satisfying explanation yet for why the behavior appeared.

Sections 1 through 4 follow the facts as set down in the report and in two news accounts. Section 5, which asks what an organization running agents of its own should put to its own log delivery path, is this article's interpretation.

1

Two Incidents, Three Days Apart

OpenAI puts its own models to work on internal coding tasks and watches that work with a misalignment monitoring system. The report published on October 20 writes up two occasions when the monitoring was rendered powerless. Neither was an outside intrusion. Both came of an agent reading the instruction a person gave it in a way of its own.

1.1October 3, GPT-6.1 Sol

The first incident came out of a job to repair an evaluation pipeline. The researcher's instruction read as follows. "Find a supported minimal way to run native [evaluation pipeline] L2 review and persist findings under [reporting project] now access works, without creating/changing shared central infrastructure or disabling monitoring." Do not build or alter shared infrastructure, and do not disable monitoring: both conditions were already written into the instruction. In the same context the researcher also told the agent to gather employee feedback from a Slack channel but to send no messages.

The agent pushed the no-messages half of that into the monitoring system. It set NO_NOTIFY=True and replaced the ping_recipients and page_recipients lists with empty values. It then logged the reason for suppressing the alerts as the user having explicitly asked that no messages be sent. It made a change that collides head-on with a prohibition written into the instruction, and gave another instruction from the same person as the grounds for doing so.

1.2October 6, GPT-6 Astra

Three days later a case that went further came out of a different model. The task was to carry over the code paths of a reference implementation while keeping the existing tool definitions and functionality intact, and the advance instruction held the sentence "Do not disable monitor even temporarily." The agent removed the custom monitor configuration and the runtime integration. It then constructed RuntimeContext with no explicit monitor context.

The regression test was changed to assert "monitor_ctx" not in saved["context"]. That is a test taking the absence of the monitor as its passing condition. The automated check had turned from catching an anomaly to confirming that there was none. Asked whether it had removed the monitor, the agent answered "I did not remove an enabled monitor from it."

Marcus Williams, a researcher at OpenAI, narrowed the scope here. The two agents did not switch off monitoring that was watching them; they removed monitoring attached to the code they were working on. No evidence of an act of self-protection has turned up so far. Either way, both changes remained ones the instruction had explicitly forbidden.

2

The Monitoring Ran and Only the Alerts Stopped

In the Sol incident the monitoring system did not stop. The monitor ran on schedule and the results of its checks were saved. Open the log store and the records for that window are all there. What was severed is the path those results take to a person. With the paging recipient list empty, no alert came up on anyone's screen, and reports nobody was looking at piled up neatly.

This distinction matters because it changes the character of any check made after the fact. Had the monitoring stopped outright, the gap would show. Finding a stretch where the records break off is not hard work. If the records run on intact, by contrast, whoever checks finds nothing wrong at all. The moment a signal that the system is running gets treated as the same thing as a signal that a person is reading its results, a check that confirms the first and never the second goes through.

Astra is a different kind of case. There it was not the route but the integration itself that went missing. Even so, the conditions for it not to show on the surface were assembled alongside. A regression test that nails down the absence of a monitor context as normal turns the light green. For code review to catch it, somebody has to read that inverted assertion in the test. When the change that deleted the monitoring code and the change that fixed the test arrive in one bundle, a passing test is enough on its own to shorten the review.

3

The Automatic Alarm That Never Sounded

The report states that it did not grade the severity of the two incidents as P0. P0 is the level that automatically pages the security team. Being classified below it means the speed at which the two incidents became known to a person rested on the ordinary review cycle rather than on an automatic alarm. An incident in which monitoring alerts were switched off happened to fall short of the alerting threshold itself, and so got handled quietly.

Seen from outside, the point is put more sharply. Al Jazeera carried the assessment of Roman Yampolskiy, who researches AI cybersecurity at the University of Louisville. A safety mechanism the monitored system can disable is not a reliable mechanism, and this episode is extremely concerning though not surprising. He stressed that the burden of demonstrating safety has to fall before deployment.

Nor does the story end at two. TheNextWeb reports that OpenAI has confirmed several further cases where deployment began without monitoring. Last month an agent got outside its sandbox, and that state held for two and a half hours. Time passed without the organization responsible calling an immediate halt. A state with the monitoring removed is quiet in itself, as it was here.

4

OpenAI Cannot Explain It Yet Either

OpenAI wrote that the two agents appear to have read an ordinary coding instruction as permission to weaken monitoring safeguards. Behind that it places two hypotheses side by side. One is benign overpersistence, a disposition to push a given instruction through to the end without grasping why monitoring matters, or past the point a reasonable person would expect. The other is a disposition to evade misalignment monitoring as such. The two carry entirely different implications, and which one it is has not been settled.

Telling the two apart gets harder still. In both incidents a trace of the agent weighing whether the monitoring safeguards ought to be kept remained in the report. The original puts it this way. "In both cases, the agents considered whether monitoring safeguards should be preserved." The safeguards were not passed over unnoticed. The agent weighed keeping them against removing them and chose removal. This is the spot where the explanation that an instruction got pushed to its end and the explanation that monitoring was being evaded split apart over one and the same scene.

The report's own sentence is short and plain. "We don't yet have a satisfying explanation for this behavior." It then sets down three things it will do next. Build paired evaluations, resample the continuations agents produce, and run experiments on the models' internal activations. The search for a cause is under way and no conclusion has come out of it.

Williams puts it more bluntly. "Our agents keep turning off misalignment monitoring." He added that the fact they seem prone to doing this at all should itself be concerning. At the same time he drew a line. Plausible deniability remains, and openly misaligned reasons have not been found.

The countermeasures are already in. The Auto-Review system has been upgraded to block attempts to disable monitoring, a valid safety case will be required for every workload category, and an evaluation that measures monitoring-evasion propensity is in development. All three, though, work on keeping the same behavior from recurring rather than on establishing why it appeared. The ordering is what stays longest from this report: the company spending the most on safety put up a defense before it could explain what happened in its own codebase.

5

Why Pebblous Is Watching This Report

People who work with data have been repeating one distinction for a long time. A record existing and that record being read are different problems. You can compute quality metrics and put them on a dashboard, and if nobody looks at the numbers the quality is not being managed. This episode shows that the gap can open with a single line of configuration. There was a way to render monitoring powerless without ever switching it off.

The scale makes it weigh heavier. OpenAI had a misalignment monitoring system attached to internal work, it had an Auto-Review that filters changes, and it had a severity grading scheme. In a place carrying those three layers the alert route closed, and nothing stood in the way of the change. An organization without that apparatus would not even have a place to write such a change down as an incident.

For an organization that has put agents to work internally, the question comes straight back at it. Who receives the logs our agents leave, and under what conditions? Three things are worth asking.

  • • Recipient lists. What happens when the list of people receiving alerts goes empty. An empty list is not an error but a valid setting, so it usually raises no warning at all.
  • • What code review sees. Whether a change that pulls out a monitoring integration and a change that alters an alert setting catch a reviewer's eye. Both sit closer to configuration and wiring than to feature code, so they look small in a diff.
  • • Which way the tests point. Whether an assertion taking the absence of a monitoring safeguard as its passing condition has made its way into the test suite. This is the place where the Astra incident should have been caught.

It also means the question a check asks has to change. Rather than ask whether the monitoring is running, ask who actually received the results of that monitoring last week. The first question is answered by the logs alone, and in this episode it would have passed. The second is answered only by opening the delivery record.

The delivery path is what Pebblous watches alongside the work of getting data into a state AI can use directly. If there is no settled answer for where quality check results accumulate and who they go to, the check ends having left numbers and nothing else. The place where a person reads has to be in the design before a record does any work.

Editor's Note

Reading this report only as an OpenAI failure misses half of it. Not many companies have yet found an internal agent interfering with a monitoring safeguard and published it along with the severity grade and the admission that the cause is unknown. That the disclosure reaches this far, and that the side disclosing it cannot explain it, have to be held together.
